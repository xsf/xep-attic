1. Introduction¶

Portable Import/Export Format for XMPP-IM Servers (XEP-0227) [1] introduced a format for the import/export of XMPP data. That specification specifically says "the contents of MUC, Pubsub, and other services are out of scope for this specification". This specification exists to cover that gap.

2. File format¶

Inside the root element from Portable Import/Export Format for XMPP-IM Servers (XEP-0227) [1] of <server-data/> qualified by the urn:xmpp:pie:0 namespace, may occur zero or more <component/> elements qualified by the urn:xmpp:pie:0#component namespace. Each <component/> element describes a component, and has a jid attribute that contains its JID and a type attribute that describes the type of component.

Components may contain children to describe any data relevant to the type of component. For example, a pubsub type component may have a <pubsub xmlns="http://jabber.org/protocol/pubsub#owner"/> child.

A component may contain elements qualified by a namespace not mentioned in this specification or in Portable Import/Export Format for XMPP-IM Servers (XEP-0227) [1]. The exported data SHOULD be meaningful without the extensions. An importing entity that encounters a namespace that it doesn't understand, or otherwise is unable to import all given data, SHOULD ignore the unknown data, SHOULD notify the operator, and MAY offer to terminate the process.

2.1 Items¶

A component may have associated items, represented by a <item/> element under the <component/> element. The <item/> element MUST have a name attribute, which contains a type-specific identifier for this item.

Items may contain children to describe any data from items in the relevant type of component. For example a muc type component may have items with a <archive xmlns="urn:xmpp:pie:0#mam"/> child.

An item may contain elements qualified by a namespace not mentioned in this specification or in Portable Import/Export Format for XMPP-IM Servers (XEP-0227) [1]. The exported data SHOULD be meaningful without the extensions. An importing entity that encounters a namespace that it doesn't understand, or otherwise is unable to import all given data, SHOULD ignore the unknown data, SHOULD notify the operator, and MAY offer to terminate the process.

3. Security Considerations¶

Exported data files are to be handled with care, since they contain data that users expect to be protected. An exporting entity SHOULD make sure that the generated file is not accessible to unauthorized persons, e.g. by encrypting the file with OpenPGP.

4. IANA Considerations¶

This document requires no interaction with the Internet Assigned Numbers Authority (IANA) [2].

5. XMPP Registrar Considerations¶

5.1 Protocol Namespaces¶

This specification defines the following XML namespace:

  • urn:xmpp:pie:0#component

The XMPP Registrar [3] includes the foregoing namespace in its registry at <https://xmpp.org/registrar/namespaces.html>, as described in Section 4 of XMPP Registrar Function (XEP-0053) [4].

5.2 Component Types¶

This specification creates a new registry for the component type attribute, with the following initial contents:

  • muc
  • pubsub
