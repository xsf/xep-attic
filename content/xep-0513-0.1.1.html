1. Introduction¶

A common feature in online communication is the ability to intentionally and explicitly address a message to a specific person or a group of people, and have the recipient's client notify them. This document provides a mechanism to allow users to intentionally reference individual users, as well as entire groups based on roles, affiliations, and hats in their messages.

This specification is primarily aimed at the markup format for mentions, as opposed to the notification of recipients, which may be covered by a future specification. There has been some success getting current versions of this specification working with push notifications, but it is not expected to work in certain scenarios as-is, such as end-to-end encrypted chats.

2. Glossary¶

A few terms are used throughout this document that are worth defining.

Mention
A mention is a reference to one or more users, which generally produces a notification for the relevant recipients.
Unintentional Mention
A type of mention which has no explicit wire-based format, and which was not necessarily intended by the sender. The most common form of unintentional mention is for a client to match messages against a regex of the user's name. For users with common words as their nickname, this can result in many false-positives, with no way for the client to determine whether a mention was intended or not. This may also be referred to as an "implicit" mention.
Intentional Mention
As opposed to unintentional mentions, intentional mentions explicitly mark a section of the body as being a mention to a particular user or group of users via a dedicated markup element. This helps to avoid false-positives by conveying the sender's intent. This may also be referred to as an "explicit" mention.

3. Discovering Support¶

An entity implementing this specification MUST advertise 'urn:xmpp:mentions:0' as a Service Discovery (XEP-0030) [1] feature. Subsequent OPTIONAL features in this document MUST also advertise support, if implemented.

4. Use Cases¶

Given that this specification is primarily concerned with the markup format, it depends on the use of Message Markup (XEP-0394) [2] <span /> elements to specify the range of effected text. Here, the <mention /> child element is specified, qualified with the 'urn:xmpp:mentions:0' namespace.

The 'type' attribute MUST be specified with a URI determining the type of mention (occupant ID, room, association, etc.). A mention MAY contain a 'target' attribute, which specifies who is being mentioned. The 'target' MUST only be omitted in the scenarios defined by the 'type' below.

Multiple mentions may be contained in the same <span />, as well:

Any mention type MAY restrict the set of targetted users to only those who are currently active, akin to "@here" on legacy messengers, by setting 'active' to true. If an entity receives a mention that was sent when the user was not active, it SHOULD NOT notify them. It is up to implementations what constitutes "currently active". Examples include being online or recently interacting with the client.

4.1 Mentioning an Individual¶

Individual mentions are the minimum REQUIRED to support this specification, advertised via the 'urn:xmpp:mentions:0' namespace.

The only supported way to mention an individual in this document is to use Anonymous unique occupant identifiers for MUCs (XEP-0421) [3] identifiers as the 'target', with a 'type' of 'urn:xmpp:mentions:0#occupant'. Mentioning a user in a 1:1 chat, or in a Multi-User Chat (XEP-0045) [4] room that does not support occupant IDs, is intentionally unsupported here, but may be defined elsewhere.

4.2 Mentioning Groups¶

Users might wish to mention whole groups of users at once. The following subsections specify several types of groups that can be mentioned, all of which are OPTIONAL.

Each group type has its own URI for the 'type' attribute, which, unless noted otherwise, MUST also be advertised via Service Discovery (XEP-0030) [1] if supported. Custom group types not specified in this document MAY be used, provided they follow the same rules.

4.2.1 Mentioning via Room Occupancy¶

It is often useful to mention all occupants of the current room at once, similarly to "@everyone" or "@room" on legacy messengers. The 'type' for this mention is 'urn:xmpp:mentions:0#channel', which MUST be advertised if this feature is supported. As the target is all room occupants, the 'target' attribute is redundant, and MUST NOT be specified.

4.2.2 Mentions via Roles and Affiliations¶

It is possible to mention occupants with specific Multi-User Chat (XEP-0045) [4] roles or affiliations. Support for this feature is advertised via 'urn:xmpp:mentions:0#associations', rather than the 'type'. The 'type' is one of the seven URNs defined in the table below. A role or affiliation mention MUST NOT contain a 'target'.

4.2.3 Mentions via Hats¶

Hats, specified in Hats (XEP-0317) [5], can also be mentioned using the 'urn:xmpp:mentions:0#hats' namespace. The 'target' attribute MUST contain the hat's URI.

5. Implementation Notes¶

This specification allows sending clients to convey a user's intent. Implementations SHOULD also allow sending participants to talk about someone without having to mention them.

Extra characters which are not part of the user's name, such as '@', could interfere with implicit mentions in some implementations.

Receiving entities always have final say on whether they think a mention refers to or notifies the user, and MAY specify further rules than specified here.

6. Design Considerations¶

Most clients currently use regex-based solutions to determine whether a user is to be notified of a message. This is prone to false positives, especially for users with common words as names. It also provides no mechanism for a user to refer to someone else without notifying them.

Attention (XEP-0224) [6] could be used to provide similar functionality to a room mention. However, it has several downsides compared to this specification, including:

  • It cannot specify the section of the message it applies to, only marking the entire message
  • It is explicitly meant for ephemeral "pokes" or "nudges", and thus can only be used for 'active' room mentions, like '@here', leaving a gap for normal room mentions
  • It only specifies the intended usage in the context of one-to-one chats, leaving much room for interpretation in the context of groupchats. This has lead to people having competing ideas for how the element should be used in such contexts, meaning a client cannot even be sure that the notification was intended for any particular purpose

References (XEP-0372) [7] provides a basic means to explicitly mention a single user via JID, but no means of mentioning via occupant ID, mentioning groups of users, nor means to extend mentions further.

7. Accessibility Considerations¶

This specification allows users to intentionally choose whether to mention a user or group, removing the need to use old regex-based name matches, which are prone to false positives. It also allows users to refer to someone else without unintentionally disturbing them, and without relying on tricks to prevent regex matches.

8. Internationalization Considerations¶

Mentions which contain an 'xml:lang' attribute correspond to body elements of the same language. Implementations SHOULD send a mention for every language it sends.

9. Security Considerations¶

Implementations, both on the server- and client-side, SHOULD take care to mitigate the possibility to abuse mentioning groups of people, such as by providing an option to disallow group mentions by unpriviledged users, or turning off notifications for them in the client.

Use of intentional mentions with OMEMO could leak metadata about who the message is directed towards, if the mention markup is left unencrypted, such as in legacy OMEMO.

Using Anonymous unique occupant identifiers for MUCs (XEP-0421) [3] instead of a regular participant JID in MUC prevents moderators possibly leaking JIDs they have access to that other occupants don't. Using occupant IDs even in non-anonymous rooms allows them to become semi-anonymous without leaking JIDs.
